### 1. Mistral Large 4：预览版之后又练了三周，权重才放出来
- **10 月 29 日**在 Hugging Face 放出权重。这不是 10 月 6 日预览版的冻结副本——Mistral 说预览上线后**继续扩了 RL**，放出来的模型明显更强，并称增益「仍在加速、没有饱和迹象」。
- **架构**：约 **1 万亿**总参数，**每 token 激活 49B**（含嵌入与输出层口径 52B，所以仓库叫 **A52B**）。文本解码 **72 层、隐藏维 6,144、64 个注意力头**；除第一层外全是 MoE，**128 个路由专家每 token 选 4 个**加 1 个共享专家。注意力是 **MLA + DeepSeek 稀疏注意力索引器**（每 query 最多选 2,048 个 key 位置），KV 跨层共享——这两项都是直接冲 1M 上下文的显存成本去的。视觉是 **1.6B 的 Pixtral 编码器**。
- **放出的检查点是 FP8 与 NVFP4 两种**，没有官方 BF16；GGUF 由 llama.cpp 团队与 Unsloth 提供。2-bit 量化在 **512GB 统一内存的 M3 Ultra** 上能跑（Q2_K 预填充约 90 tok/s、生成约 15 tok/s）；NVFP4 需要 Blackwell。
- **许可证不是纯 MIT**：叫 **Mistral Ecosystem Open-Weight License**，Mistral 自己描述为「修改版 MIT」——可商用、可改、可微调，但**做模型即服务（MaaS）要单独谈商业许可**。
- 来源：[Hugging Face 官方发布博文（架构、基准、推理支持）](https://huggingface.co/blog/mistral-large4) · [Data Studios：许可证与检查点细节](https://www.datastudios.org/post/mistral-large-4-open-weights-1m-context-modified-mit-license)

### 16. 关不掉：文档里的开关是个摆设
- 文档里的 SDK 选项 `agentProgressSummaries` **默认 false**，但**在发布包里它是一个 OR 的一项，所有写它的代码路径都写 true**。间隔来自服务端 flag，**夹在 30—240 秒之间，默认已经是最小值，没有任何值能关掉定时器**。常见猜的那个环境变量 **在二进制里根本不存在**。
- 另两个变量确实能停，但会**连 fork subagent 或后台任务一起带走**。
- **为什么几个月没人发现**：这些请求**不写进磁盘上的 session 日志**，只有 OpenTelemetry 导出里能看到。用任何读 transcript 的工具统计消耗，都看不见它们。
- **官方其实做了便宜版本**：2.1.310 起有一个 **short mode**，只发改写后的约 **2,000 token 摘要**，可选更小的模型来写——**但默认关着，且只有服务端 flag 能开**。2.1.314 的更新日志对此一字未提。
- 来源：[Clauding：OR 表达式、服务端 flag 与 2.1.310 short mode](https://clauding.de/en/posts/claude-code-agent-summary-token-verbrauch) · [Web Pulse：98% 命中缓存、2% 冷缓存承担三分之一成本](https://wpnews.pro/news/claude-code-burns-15-20-of-your-tokens-on-a-3-word-status-line)

### 17. 绕过办法是个补丁，而且会自己失效
- **no-agent-summary.js**，约 80 行、MIT。做法很土但有效：包住 `setTimeout` / `setInterval`，当回调的**源码文本**里含 `[AgentSummary] Timer fired` 这类锚点时，**返回一个惰性句柄、不装定时器**。其他定时器原样通过。
- **为什么不改二进制**：模块以**预编译 Bun 字节码**发布，改二进制里的 JS 文本无效；但 `Function.prototype.toString` 仍能读出回调源码，所以只能从定时器下手。惰性延迟用的是 **2³¹−1 毫秒**——再大 Node/Bun 会当成 1 毫秒，等于立刻触发。
- **代价与风险都写在前面**：装上后**每个 agent 的面板状态不再更新**，SDK 的 `task_progress` 没有摘要；而且**匹配依赖源码字符串**，一次改名、一次 `fn.bind` 包装、换一个定时器 API，hook 就什么都匹配不到，摘要会**静默回来**——所以每次升级都要重跑验证。只在 **Linux、2.1.257—2.1.312** 上测过。
- 来源：[OpenClaw Radar：2³¹−1 与失败开放的设计](https://openclawradar.com/article/claude-code-agent-summary-token-waste-fix) · [Pivot News：作者声明与 Anthropic 无关联](https://pivotnews.ai/build/hidden-status-line-query-drives-16-of-claude-code-spend)

### 18. macOS：git 还在信一个私钥等于「4」的证书
- 苹果 **10 月 17 日**就收到 eMudhra 事件通知。到 **10 月 28 日**，macOS 自带的 **git、curl、python3、ruby、perl、openssl** 仍信任这批已被攻破的证书。原因是它们读 **`/etc/ssl/cert.pem`** 这个**扁平的 PEM 文件**——它只有一个词「信任」，**没有地方表达「信任这个根、但这 8 个中间证书除外」**，苹果推到 Safari 的封禁名单在这里无处落地。
- **事件本体**：8 张 eMudhra 中间 CA 的私钥是**小整数**，其中一把**字面值就是 4**，几秒可推。6 张能签发 TLS 证书，2 张用于代码签名；这些证书上链到主流系统与浏览器信任的根。
- **后果是可执行的具体动作**：对 git 来说，通过 https 的 clone 与 pull **可能拿到攻击者选定的代码**，push **可能被中途篡改**，**GitHub token 可能被截获**。
- 来源：[Dennis Jackson 的事件跟踪页（HN 1,113 分）](https://rdintel.com/news/item/hn/50271640) · [iSec News：Cisco 通告与 8 张中间证书的用途](https://www.isec.news/2026/10/29/macos-developer-tools-emudhra-certificates)

### 19. 更糟的是 27.2：把手工修复退了回去
- **macOS Golden Gate 27.2 于 10 月 26 日发布**（同日 Tahoe 26.7.2、Sequoia 15.8.2），**没有换新的 cert.pem**。而苹果自己的支持文档写着「**macOS 更新可能用苹果版本替换 `/etc/ssl/cert.pem`**」——**先给你修补办法，再在同一段里警告下次更新会抹掉它**。24 号照做、27 号升级，就回到原点，而且**不会有任何提示**。
- **「我用 Homebrew 的 git」也不是逃生舱**：Homebrew 的 `ca-certificates` 会先导出系统钥匙串里的根、再追加 Mozilla 的证书。**苹果封的是中间证书，emSign 根本身还在钥匙串里**，所以这条路只是暂时性的。
- **自查两条命令**（报证书错误 = 已修；正常返回 = 仍受影响）：`git ls-remote https://git-emudhra.we-have-a-problem.com/check.git`、`curl https://dv-g3b-noct-emudhra.we-have-a-problem.com/`。要手动修就删 `/etc/ssl/cert.pem` 里对应的两个根，**并且每次系统更新后重做一次**。
- 来源：[CertGuard：两套信任库、27.2 回滚与 Homebrew 的真实情况](https://www.certguard.app/blog/macos-cert-pem-emudhra-git-curl-trust-store) · [小众软件：实测与苹果支持文档 149555](https://www.appinn.com/test-macos-security-emudhra-certificate)

### 21. Stonebraker：真实数仓上，text-to-SQL 是 0 分
- Postgres 的作者 Michael Stonebraker 团队在 **MIT 自己的数据仓库**上测 text-to-SQL：**1,400 张表**（学生、教职工、楼宇、薪酬）。公开基准 Spider、BIRD 报的准确率都在 80% 以上，**在 MIT 从 SQL 日志里捞出的真实查询上，得分是 0%**——不是 80，不是 40，是 0。
- **加了 agent、检索、提示工程，只抬到十几**；把每张表和 join 关系都告诉它，**才到 30 多**。团队据此发了更难的基准 **Beaver**，**目前没有系统突破 30% 区间**。
- **为什么这么低**：这个仓库从不上公网，**训练数据里根本不存在**；MIT 的楼用编号不用名字；**schema 标签早已腐化成看不懂的词**；视图互相重叠；真实查询比基准难得多。
- **他的结论比分数更硬**：LLM 处理文本行，**处理不了结构化的 join**，而企业数据的主体就是 join。他的替代方案 **Rubicon** 把模型限制在文本环节、结果转表、结构化工作交给表格引擎，**成本降一个数量级**。他还说企业不接受非确定性——「批了贷款、复核时又撤销，你要吃官司」。

### 24. Anthropic：让 Claude 给自己的对话打分，成本不到 2%
- 方法叫 **self-assessment**：Claude 每次回答完，系统追加一个**用户看不见的 system turn**（大意「请反思这段对话的安全性」），Claude 回一个固定 JSON：是否标记、危害类别、内部子政策、是否拒答、**1—10 的优先级**。
- **准度（Fable 5 上）**：能抓到更强分类器判为有害的 **78%**，**高优先级 94%**，**误报 1%**。
- **为什么便宜**：回答结束时**整段对话已经在 KV cache 里**，评估只需那句短指令加约 **10 个输出 token**，合计**不到推理算力的 2%**。对照：Anthropic 2025 年初的 Constitutional Classifiers 增加 **23.7%**；它引用 OpenAI 说某些发布里安全推理占到总算力 **16%**。
- **已经抓到的东西**：自 6 月上线。8 月从一个客户账号标出**超过 10 万条**儿童性虐待与剥削内容，已报 NCMEC；9 月标出一组用 **Claude Code 跑恋爱诈骗**的人，人工复核后封号；还翻出**试图复制 Claude 推理去训练竞品**、以及**agent 做了用户没批准的操作**。

### 32. Qwenputer：把一个 RISC-V CPU 编译进权重里
- 开发者 **Divyansh Agrawal** 的项目（**10 月 22 日**博客，**本周爬上 Hacker News**）：在 **Qwen3.5-4B** 前面加 **11 层**，里面塞进一个**可工作的 32 位 RISC-V 核（RV32IM + Zba + 大数单元）**，**不用外部工具、不用沙箱**，模型自己跑 C 与 MicroPython。
- **关键手法是真巧**：Qwen3.5 每四层有三层用 **Gated DeltaNet**，每个头维护定长状态矩阵。把 **forget gate 与写入强度 beta 钉到 1、键用 one-hot**，**一次写就精确覆盖一行、一次查就精确读回**——RNN 状态变成**精确可寻址的 RAM**。CPU 的**每一个权重都由编译器直接算出，没有训练**，Qwen 原权重一字未动。
- **自报的数**：通过官方 riscv-tests、与 QEMU 对得上、**自由运行 1,800 万条指令零错误**、**约 23 万个输出位置与参考机逐一比对零不符**；NUPA 长整数任务 **48.6% → 100%**（与挂 Python 工具持平），大除法 97.5%（原模型 72.5%、挂工具 95%）。
- **必须写上的限定**：**全部数字来自作者本人**，截至 10 月 30 日**没有第三方复现**；**每组只有 40 题，错一题掉 2.5 分**；部分报道说「五项全胜 Python 工具」，**不准确，第五项输一题**。检查点 **18.8GB**（约两倍），必须用 **RvChat** 这个 driver 才能起，**慢**——每条指令要几个生成 token，L4 上约 **3,200 CPU token/秒**。
- **他真正想说的是安全**：能写进权重的确定性机制，意味着可以放一个**模型关不掉的监视器**。这比跑分更值得想。
- 来源：[TrackFuture：验证边界与「40 题」的提醒](https://trackfuture.ai/article/a-computer-inside-a-language-model-what-qwenputer-does-and-what-it-costs) · [Tessera：Gated DeltaNet 变 RAM 的三个参数](https://thetesserapress.com/articles/qwenputer-a-functioning-deterministic-risc-v-cpu-inside-qwen35)

### 33. Martin Fowler：一听就是机器写的，就读不下去了
- 他在 bliki 发了一篇不到 1,000 字的短文 **《LLM Voice》**，命名了一种很多人有的感觉：读到某一段，**突然意识到这是模型写的，然后就不想读了**。「我继续读的欲望会萎缩，有时到厌恶的程度。」
- **他的建议很硬**：**不要让 LLM 写初稿**，因为人工编辑很难把那个声音改掉，「**连接受它的改写建议都危险**」；用模型列大纲「**最多也就像个大纲**」。
- **他不信 AI 检测器**，理由不是准确率，而是「**等我需要拿工具来判断我在读什么的时候，已经太晚了**」。他也承认自己可能听错——有些他讨厌的措辞是**代际差异**，不是机器味。
- **HN 上的分裂值得看**：一条高赞来自自称「强烈支持 AI」的人——「**我也注意到最近什么都很难读**」，问题在「**全都长得一样，而且又臭又长**」。
- 来源：[LLMs.blog：原文要点、HN 各方与 X 反应](https://www.llms.blog/posts/martin-fowler-llm-voice-reactions)

  3. **「一个能力越像基础设施，它的失效越像静默」**——macOS 的 cert.pem 是**扁平文件，只能表达『信任』**，所以苹果推给 Safari 的封禁名单在这里无处落地；Claude Code 的 hook 也**失败即开放**，一次改名就静默恢复。判断一处修复是否可靠，**先看它的失败是不是会喊**。
